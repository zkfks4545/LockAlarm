# 루틴 알람 프로젝트 헌장

## 핵심 원칙

### I. 알람 신뢰성이 장식보다 우선한다

알람의 핵심 가치는 지정된 시각에 사용자를 깨우거나 주의를 환기하는 것이다. 시각 콘텐츠, 애니메이션, 외부 앱 연동보다 예약 정확성, 잠금 화면 진입, 재생 지속성, 재부팅 복구, 해제 가능성이 항상 우선한다. 지원 대상으로 선언한 기기와 OS에서는 일반 상태뿐 아니라 화면 잠금, 절전 대기, 앱 프로세스 종료, 재부팅 시나리오를 검증해야 한다. 신뢰성 검증 기준을 통과하지 못한 기능은 완료로 간주하지 않는다.

### II. 사용자의 기기 제어권을 침해하지 않는다

밝기와 미디어 음량은 알람이 시작될 때 초기값으로 한 번만 적용한다. 실행 중 값을 감시하거나 반복 적용해서 사용자의 조작을 되돌려서는 안 된다. 앱이 변경한 기기 상태는 변경 전 스냅샷과 복원 정책을 명시적으로 기록해야 하며, 알람 해제 시 사용자가 선택한 `복원` 또는 `현재 값 유지` 정책을 예측 가능하게 적용해야 한다. 앱 오류가 사용자의 기기 설정을 영구적으로 알 수 없는 상태에 두지 않도록 복구 경로를 설계한다.

### III. 플랫폼 규칙과 최소 권한을 따른다

정확 알람, 전체화면 알림, 포그라운드 서비스, 알림, 시스템 설정 변경 권한은 Android의 공개 API와 사용자 승인 흐름만 사용한다. 권한을 우회하거나 제조사 제한을 숨겨서 동작하는 것처럼 표시해서는 안 된다. 각 특별 접근은 필요한 시점과 이유를 설명하고, 거부·회수·지원되지 않는 경우의 제한 상태와 복구 동선을 제공해야 한다. 권한이 없을 때 조용히 실패하는 예약은 금지한다.

### IV. 로컬 우선과 콘텐츠 경계를 지킨다

알람 정의, 사용자 설정, 로컬 콘텐츠 접근 권한은 기기 안에 보관하며 계정, 서버, 분석 SDK는 명시적인 새 요구가 생기기 전까지 도입하지 않는다. YouTube 모드는 지정 URL을 공식 앱 또는 사용 가능한 URL 처리 앱에 넘기는 기능으로 한정한다. YouTube 콘텐츠 다운로드, 캐시 우회, 음원 추출, MP3 변환은 범위 밖이며 구현하지 않는다. 사용자가 선택한 파일은 원본을 복제하기보다 Android 문서 접근 권한으로 참조한다.

### V. 명세 추적성과 검증 증거를 유지한다

`spec.md`를 제품 동작의 원본 계약으로 삼고 `plan.md`, `tasks.md`, 테스트와 코드는 그 계약에서 파생한다. 모든 기능 요구사항은 최소 하나의 수락 시나리오 또는 측정 가능한 성공 기준에 연결되어야 한다. 사용자 스토리는 가능한 한 독립적으로 구현·시연·검증할 수 있어야 한다. Android 플랫폼 경계와 기기 상태 변경은 단위 테스트만으로 완료 처리하지 않으며 실제 기기 검증 기록을 남긴다.

### VI. MVP의 단순성을 지킨다

검증되지 않은 미래 요구를 위해 모듈, 데이터베이스, 백엔드 또는 추상화 계층을 미리 추가하지 않는다. 초기 제품은 한 Android 앱과 로컬 저장소로 유지한다. 복수 Gradle 모듈, Room, 별도 도메인 프레임워크는 복수 알람·반복 규칙·마이그레이션 요구로 현재 구조가 실제 한계에 도달했을 때만 도입하며, `plan.md`의 복잡성 추적 표에 이유를 남긴다.

## 제품 및 기술 제약

- 제품은 우선 단일 사용자의 개인 Android 휴대전화에서 동작한다.
- 핵심 사용자 흐름은 네트워크 연결 없이도 예약·로컬 알람·해제가 가능해야 한다.
- 한국어 UI를 기준으로 기획하고, 접근성 레이블과 큰 글꼴에서도 핵심 해제 흐름을 사용할 수 있어야 한다.
- 외부 앱의 설치 여부나 동작 성공을 보장하지 않으며, 이관 실패를 명확히 처리한다.
- 기기 상태를 바꾸기 전 원래 값을 읽고 세션을 영속 기록하는 순서를 지킨다.
- 알람 해제는 언제나 로컬에서 가능해야 하며 외부 앱이나 네트워크 성공에 의존해서는 안 된다.

## 개발 및 검토 절차

1. 기존 프로젝트에는 Living Spec 방식을 사용한다. 의도 변경은 먼저 `spec.md`에 반영한다.
2. 계획 전에 `[NEEDS CLARIFICATION]` 항목을 최대 5개의 고영향 질문으로 해소한다.
3. `plan.md`는 헌장 준수 여부, 기술 선택의 근거, 실제 디렉터리 구조와 검증 전략을 포함해야 한다.
4. `tasks.md`는 사용자 스토리별로 구성하고 각 작업에 요구사항 또는 스토리 식별자를 연결한다.
5. 구현 전 `spec.md`, `plan.md`, `tasks.md`의 불일치와 누락을 분석한다.
6. 구현 후 빌드·정적 검사·자동 테스트와 지원 기기 수동 검증 결과를 함께 확인한다.

## 거버넌스

이 헌장은 다른 프로젝트 문서와 구현 관행보다 우선한다. `MUST` 성격의 원칙을 위반하는 계획은 구현 전에 수정해야 한다. 헌장 개정에는 변경 이유, 영향을 받는 명세·코드·테스트, 마이그레이션 필요 여부를 기록한다. 원칙의 의미를 바꾸는 개정은 주 버전을, 적용 범위를 확장하는 개정은 부 버전을, 오탈자와 설명 보완은 패치 버전을 올린다.
